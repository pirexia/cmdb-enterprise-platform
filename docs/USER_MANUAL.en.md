## 1. First Access

### Accessing the platform
Open your browser and navigate to:
```
http://cmdb-server:3001
```
(or the URL provided by your systems team)

### Default credentials
After the initial installation, the system creates these sample users in the `seed`:

| Email | Password | Role |
|-------|----------|------|
| `admin@cmdb.local` | `Admin1234!` | ADMIN |
| `auditor@cmdb.local` | `Audit1234!` | AUDITOR |

> ⚠️ **IMPORTANT:** Change the passwords immediately after your first login.

### MFA flow on first login

#### Administrator users (ADMIN) — MFA mandatory
On first access, the platform **requires** you to configure two-factor authentication before entering the application:

1. Enter your email and password → the screen switches to the **MFA setup wizard**
2. Scan the QR code with your authenticator app (Google Authenticator, Aegis, Authy, Microsoft Authenticator…)
3. You can also enter the manual key (hide it with the eye icon)
4. Click **"I've scanned it → Continue"**
5. Enter the 6-digit code generated by the app to confirm
6. Optionally enable **"Trust this device for N days"** to skip the code on this machine
7. Click **"Activate MFA and sign in"** → full access to the application

> 🔒 There is no option to skip this step for administrators. It is mandatory per security policy.

#### Standard users (AUDITOR / VIEWER) — MFA recommended
On first access, the platform **suggests** configuring MFA:

1. Enter your email and password → access granted + suggestion screen
2. You can choose **"Set up MFA now"** (follows the same QR wizard) or **"Skip for now"**
3. The suggestion is shown **only once**. It will not appear again on subsequent logins.

### Signing in with MFA already configured
If your account has MFA enabled and the device **is not trusted**:
1. Enter your email and password
2. The screen switches to the TOTP verification step
3. Open your authenticator app and copy the 6-digit code
4. Optionally enable **"Trust this device for N days"** to skip this step on future logins from this machine
5. Click **"Verify code"**

> The code changes every 30 seconds — enter it before it expires.

### Trusted devices
When you mark a machine as trusted, the device token is stored in the browser. During the configured period (`TRUSTED_DEVICE_TTL_DAYS`, default 30 days), the MFA step is automatically skipped on that device. Signing out removes the trust token from the browser.

### Signing in with LDAP/Active Directory
If the organisation has the LDAP/AD connector enabled, you will see the message **"Supports corporate credentials"** on the login screen. In that case:

1. Enter your corporate email and network password (the same as your PC/domain)
2. The system first checks the corporate directory (AD/LDAP)
3. If it is your first login, a user record is automatically created with the **VIEWER** role
4. An administrator can elevate your role in **Settings → Users**
5. If your account has MFA enabled, the TOTP code will be requested in a second step

> **Fail-safe behaviour:** If the LDAP server is unavailable, the system automatically falls back to local authentication without delay. Accounts ending in `@cmdb.local` or `@cmdb.internal` are always authenticated locally, regardless of the LDAP configuration.

> **Account origin:** In **Settings → Users**, accounts provisioned by LDAP appear marked as 🏢 LDAP, while local accounts appear as 🔑 Local.

## 3. Profile and MFA Management

### Accessing your profile
- Click on **"My Profile"** in the sidebar menu

### Changing your password (local users)

> This function is only available for **local** accounts. Users authenticated via LDAP/AD must change their password on the domain controller.

1. Go to **My Profile → Change Password**
2. Enter your current password
3. Enter the new password (the strength indicator shows in real time whether the requirements are met)
4. Confirm the new password
5. Click **"Change password"**

#### Password policy

| Requirement | ADMIN | AUDITOR / VIEWER |
|-------------|:-----:|:----------------:|
| Minimum length | 16 characters* | 12 characters* |
| Uppercase letters (A-Z) | ✅ | ✅ |
| Lowercase letters (a-z) | ✅ | ✅ |
| Numbers (0-9) | ✅ | ✅ |
| Special characters (!@#$%…) | ✅ | ✅ |
| Must not be a common password | ✅ | ✅ |
| Password history | Last 20* | Last 20* |

> \* Values marked with an asterisk are configurable in the server `.env` file: `PASSWORD_MIN_LENGTH_ADMIN`, `PASSWORD_MIN_LENGTH_VIEWER`, `PASSWORD_HISTORY_COUNT`.

**The strength indicator** shows in real time whether each requirement is met, using a colour code (red → orange → yellow → blue → green).

### Enabling Two-Factor Authentication (MFA) from the profile
If you already have access to the application (e.g. you are a VIEWER and skipped the initial suggestion), you can enable MFA at any time:

1. Go to **My Profile → Two-Factor Authentication**
2. Click **"Enable MFA"**
3. Scan the QR code with your authenticator app (Google Authenticator, Microsoft Authenticator, Aegis, Authy…)
4. Enter the 6-digit code generated by the app to confirm
5. From now on, every login from an unrecognised device will require the MFA code

> ⚠️ If you lose access to your MFA app, contact an Administrator to have MFA disabled on your account.

## 5. Governance Flow: Registration Order

To get the most out of the platform and avoid orphaned records, the following **registration order** is recommended:

```
Step 1: Master Data (ADMIN only)
│
├── 1.1 CI Types (optional — the system includes predefined types)
│   → Go to Master Data → CI Types to add, edit, or delete types
│   → Available categories: Infrastructure, User Devices, Mobility/IoT,
│      Meeting Rooms, Software, Licenses
│
├── 1.2 Support Areas
│   E.g.: "Central Zone", "Madrid Datacenter", "LATAM Support"
│
├── 1.3 Branches / Locations
│   E.g.: "Madrid Office (MAD)", "Barcelona Office (BCN)"
│   → Each branch is linked to a Support Area
│
├── 1.4 Manufacturers
│   E.g.: Dell, HP, Cisco, Microsoft
│   → Use "✨ Suggest Popular" to insert 30 IT manufacturers at once
│
├── 1.5 Device Models
│   E.g.: "PowerEdge R740" (Dell), "ProLiant DL380 Gen10" (HP)
│   → Each model is linked to a Manufacturer
│   → Use the EOL Lookup Center to verify support dates
│
└── 1.6 Vendors
    E.g.: Telefónica, AWS, Microsoft Azure
    → Will be used when registering Contracts

Step 2: Contracts (ADMIN only)
│
└── Register contracts with vendors
    → Include start date, end date, and vendor
    → Addenda are contracts linked to a parent contract

Step 3: Configuration Items / CIs (ADMIN only)
│
└── Register each technology asset
    → Select Type, Environment, Criticality, Branch, and Model
    → Link to the corresponding Contracts
    → EoL/EoS dates can be filled in manually or looked up at endoflife.date

Step 4: Integrations (ADMIN only)
│
├── Upload Greenbone report (JSON) → Imports CVE vulnerabilities into CIs
└── Upload CrowdStrike report (JSON) → Updates Falcon agent status on CIs
```

> **Why this order?** CIs depend on Branches, Models (which depend on Manufacturers), and Contracts. If CIs are registered before the Master Data, the linkages will be lost.

## 6. CI Inventory Management

### Viewing the inventory
1. Click **"CI Inventory"** in the sidebar menu
2. The table shows all assets with:
   - Name, slug, CI type, and support badge (EoL)
   - Environment (Production, Staging, Testing, Development)
   - Criticality (Mission Critical, High, Medium, Low)
   - Greenbone vulnerabilities (count by severity)
   - CrowdStrike Falcon agent status

### Searching for assets
- Use the search field in the top right
- The search filters by name in real time
- All active filters are respected when exporting to CSV

### Creating a new CI (ADMIN only)
1. Click **"New CI"** (blue button, top right)
2. Fill in the required fields:
   - **Name** (unique, descriptive: `srv-prd-web-01`)
   - **Slug** (URL identifier: `srv-prd-web-01`)
   - **CI Type** — grouped selector by category:
     - *Infrastructure*: Physical Server, Virtual Server, Database, Network Equipment, Storage, Backup, Base Software
     - *User Devices*: Laptop, Desktop, Monitor, Keyboard/Mouse, Printer/Scanner
     - *Mobility/IoT*: Smartphone, Tablet, IoT Sensor
     - *Meeting Rooms*: Projector/Screen, Video Conferencing System
     - *Software*: Web Application, Microservice/API, Desktop Software, Container/Docker
     - *Licenses*: Software License
   - **Environment** (Production, Staging, Testing, Development)
   - **Criticality** (Low, Medium, High, Mission Critical)
3. Optional but recommended:
   - Hardware: Manufacturer, Model, Serial Number (only for hardware categories)
   - Software: Version, License Type (only for software categories)
   - EoL / EoS dates (or leave blank to be filled in automatically from endoflife.date)
4. Click **"Create CI"**

### The support traffic light
Each CI displays a support badge:
- 🟢 **Active** — More than 6 months of support remaining
- 🟠 **EoL in Xd** — Less than 6 months until the end-of-support date
- 🔴 **Out of support** — The EoL or EoS date has already passed

## 7. Bulk Import by CSV

Bulk import allows you to load hundreds of CIs from an Excel/CSV file.

### Step 1: Download the template
1. In **CI Inventory**, click **"CSV Template"** (the "CSV Template" button)
2. A file `plantilla-cis.csv` is downloaded with the fields and examples

### CSV fields

| Field | Required | Description | Example |
|-------|----------|-------------|---------|
| `name` | ✅ | CI name | `srv-prd-web-01` |
| `ciType` | Recommended | CI type | `PHYSICAL_SERVER` |
| `criticality` | ✅ | `LOW`, `MEDIUM`, `HIGH`, `MISSION_CRITICAL` | `HIGH` |
| `environment` | ✅ | `DEVELOPMENT`, `TESTING`, `STAGING`, `PRODUCTION` | `PRODUCTION` |
| `manufacturer` | Optional | Exact manufacturer name | `Dell` |
| `serialNumber` | Optional | Serial number | `SN-DL-00001` |
| `model` | Optional | Device model | `PowerEdge R740` |
| `version` | Optional | Software version | `2.1.0` |
| `licenseType` | Optional | License type | `subscription` |
| `status` | Optional | `active` or `inactive` | `active` |

### Valid CI types (`ciType` code)
Use the internal type code as it appears in the database. Predefined types include:
`PHYSICAL_SERVER`, `VIRTUAL_SERVER`, `DATABASE`, `NETWORK_EQUIPMENT`, `STORAGE`, `BACKUP`, `BASE_SOFTWARE`, `LAPTOP`, `DESKTOP`, `PRINTER_SCANNER`, `SMARTPHONE`, `TABLET`, `IOT_SENSOR`, `PROJECTOR_SCREEN`, `VIDEO_CONFERENCING`, `WEB_APP`, `MICROSERVICE`, `DESKTOP_SOFTWARE`, `CONTAINER`, `LICENSE`

> To get the exact list of types available in your instance, go to **Master Data → CI Types**.

### Step 2: Fill in and upload the CSV
1. Fill in the CSV with your data (you can use Excel)
2. Save as **CSV UTF-8**
3. In **Inventory → Import CSV**, select your file
4. The results bar shows:
   - ✅ `X CIs imported successfully`
   - ❌ `Y errors` (with error description)

### Common error handling
| Error | Cause | Solution |
|-------|-------|----------|
| `Slug already exists` | The name already exists in the database | Change the CI name |
| `Invalid criticality` | Unrecognised value | Use exactly: `LOW`, `MEDIUM`, `HIGH`, `MISSION_CRITICAL` |
| `Invalid environment` | Unrecognised value | Use exactly: `DEVELOPMENT`, `TESTING`, `STAGING`, `PRODUCTION` |
| `Missing required field` | Required field is empty | Fill in `name`, `criticality`, and `environment` |

## 8. Relationship and Topology Management

The platform supports N:M relationships between CIs to model infrastructure topology and analyse the impact of changes.

### Supported relationship types

| Type | Description | Example |
|------|-------------|---------|
| **HOSTS** | The source CI hosts/contains the target CI | Physical server → Virtual machine |
| **DEPENDS_ON** | The source CI depends on the target CI | Web application → Database |
| **CONNECTED_TO** | The source CI is connected to the target CI | Server → Network switch |
| **PROVIDES_SERVICE** | The source CI provides a service to the target CI | DNS Server → Clients |
| **BACKED_UP_BY** | The source CI is backed up by the target CI | Production server → Backup system |

### Viewing a CI's relationships

In the **Dependency Map**, select the CI to view its full graph of incoming and outgoing relationships (see section 15).

### Creating a new relationship (ADMIN only)

**From the Inventory:**
1. In the CI table, locate the CI that will act as the **source**
2. Click the **link** icon in the actions column (next to the edit/delete buttons)
3. The **"New Relationship"** modal opens with the source CI pre-selected
4. Select the **relationship type** from the dropdown
5. Search for and select the **target CI** using the autocomplete search field
6. Click **"Create Relationship"**

**From the Dependency Map:**
1. Select a CI in the map selector
2. Click **"New Relationship"** (top right button of the graph)
3. Complete steps 4–6 from the above flow

### Deleting a relationship (ADMIN only)

Relationships can be deleted from two points in the interface:

**From the Dependency Map — Graph View:**
- Click directly on the **edge (arrow)** connecting two CIs
- Confirmation is requested before deletion

**From the Dependency Map — Table View:**
- Locate the relationship in the table
- Click the trash icon (🗑️) in the **"Actions"** column
- Confirmation is requested before deletion

> The graph and table update automatically after deletion.

### Practical use cases

**Example 1: Mapping virtualisation**
```
[PROD-SRV-FISICO-01] --HOSTS--> [PROD-VM-WEB-01]
[PROD-SRV-FISICO-01] --HOSTS--> [PROD-VM-APP-01]
[PROD-SRV-FISICO-01] --HOSTS--> [PROD-VM-DB-01]
```

**Example 2: Application dependencies**
```
[APP-WEB-FRONTEND] --DEPENDS_ON--> [APP-API-BACKEND]
[APP-API-BACKEND]  --DEPENDS_ON--> [POSTGRESQL-CLUSTER]
```

**Example 3: Network topology**
```
[SERVIDOR-01] --CONNECTED_TO--> [SWITCH-CORE-01]
[SERVIDOR-02] --CONNECTED_TO--> [SWITCH-CORE-01]
[SWITCH-CORE-01] --CONNECTED_TO--> [ROUTER-PRINCIPAL]
```

> **Impact analysis:** If the `POSTGRESQL-CLUSTER` has a maintenance window, you can see which applications depend on it and notify their owners.

## 9. Vulnerability Management

### Viewing the vulnerability panel
1. Click **"Vulnerabilities"** in the sidebar menu
2. A list of all CIs with detected CVEs is displayed

### Vulnerability lifecycle statuses
| Status | Description |
|--------|-------------|
| 🆕 **New** | Newly imported vulnerability, unassigned |
| 👤 **Assigned** | Assigned to a technician for analysis |
| ⚙️ **In Progress** | The technician is working on the resolution |
| ⏸️ **On Hold** | Blocked by external dependencies |
| ✅ **Resolved** | Vulnerability resolved or mitigated |

### Changing the status of a vulnerability (ADMIN only)
1. In the vulnerability panel, locate the CVE
2. Use the status selector in the "Status" column
3. The change is recorded immediately and is logged in the Audit Log

### Importing from Greenbone OpenVAS
1. Export the report from Greenbone in JSON format (see `docs/mocks/greenbone_sample.json` for the format)
2. Go to **Integrations → Greenbone OpenVAS**
3. Paste the JSON into the editor or upload the file
4. Click **"Import"**
5. The system matches by hostname with existing CIs
6. New vulnerabilities are added with the status "New"

### Importing from CrowdStrike Falcon
1. Export the report in JSON format (see `docs/mocks/crowdstrike_sample.json`)
2. Go to **Integrations → CrowdStrike Falcon**
3. Upload the JSON
4. The Falcon agent status is updated on the corresponding CIs

## 11. Lifecycle Lookup Center (EOL/EoS)

The Lifecycle Lookup Center allows you to verify end-of-support dates for hardware and software from multiple sources.

### Accessing the Lookup Center
1. Go to **Master Data → Models**
2. Click on any model row (or on the **🌐 Look up** button)
3. The **"Lifecycle Lookup Center"** opens

### Three lookup sources

#### 🖥️ endoflife.date (Software / OS / Firmware)
- Community database with EOL data for Windows, Linux, MySQL, etc.
- Click **"🔍 Search on endoflife.date"** to open in a new tab
- Or use **"📥 Import versions"** to bring the versions directly as models

#### 🏢 Park Place Technologies (Enterprise Hardware)
- Specialised in enterprise hardware: Dell, HP, Cisco, IBM, NetApp
- Click **"🔍 Search on Park Place"** to search for the model directly

#### 📦 Cloud-Shelf (General Hardware)
- General hardware search engine with lifecycle and availability information
- Click **"🔍 Search on Cloud-Shelf"**

### Suggest Standard Dates
When external sources do not have clear data:
1. In the **New Model** form, select the **Type** (Software / Hardware)
2. Click **"✨ Suggest Standard Dates"**
3. The system calculates standard dates:
   - **Software**: EoL = today + 2 years
   - **Hardware**: EoL = today + 5 years (warranty + extended support)
4. Use these dates as an indicative reference

### Synchronise EOL with endoflife.date
After confirming the dates with the external sources:
1. In the model list, click **"🔄 EOL"** for the corresponding model
2. The system queries endoflife.date automatically
3. It updates the `eolDate` and `eosDate` fields for all CIs that use that model

## 12. Automated Daily Alerts

The alert engine automatically sends a daily email report with assets that require attention.

### When is it sent?
- **By default**: Every day at **08:30 AM** (Madrid time)
- The systems administrator can change the schedule with the `ALERT_CRON_SCHEDULE` variable

### What does the report include?
The email contains three sections (if there are items to report):

1. **🗓️ End of Support / End of Life** — CIs whose EoL or EoS date expires within the next 30 days
2. **📄 Contracts Expiring Soon** — Contracts that expire within the next 30 days
3. **🛡️ Pending Critical/High Vulnerabilities** — CIs with unresolved CRITICAL or HIGH CVEs

### Report colour codes
| Colour | Meaning |
|--------|---------|
| ⛔ Red (EXPIRED) | Already expired (0 days remaining or fewer) |
| 🔴 Orange-red (CRITICAL) | Expires in less than 7 days |
| 🟠 Orange (UPCOMING) | Expires in 8–30 days |

### What to do if you are not receiving emails?
1. Contact the Systems Administrator to verify the SMTP configuration
2. The admin can test sending from **Settings → Integrations → "📧 Send Test Email"**
3. Check your spam folder

## 15. Dependency Map

The Dependency Map allows you to explore relationships between CIs in two modes: **interactive visual graph** and **exportable table**. It supports multi-level traversal to visualise transitive dependencies several hops away from the selected CI.

### Accessing
Click **"Dependency Map"** in the sidebar menu.

---

### Step 1 — Select CI and depth

Upon entering, the configuration form is shown with two controls:

**CI search:** type part of the name or slug to filter and select the CI you want to explore.

**Dependency depth:** determines how many hops are traversed from the selected CI.

| Option | Description |
|--------|-------------|
| **1 level** | Direct relationships only (outgoing and incoming) |
| **2 levels** | Direct relationships + relationships of neighbouring CIs |
| **3 levels** | Up to 3 hops from the root CI |

> The greater the depth, the more CIs and relationships appear. For highly connected CIs, start with 1 level and expand progressively.

Click **"View dependencies of…"** to load the graph.

---

### Step 2 — Explore: Graph View

The graph places the selected CI as the central node (indigo border + "origin" badge) and arranges the other CIs in columns according to their direction and distance:

- **Columns on the left**: CIs pointing *towards* the root CI (incoming)
- **Central column**: Root CI
- **Columns on the right**: CIs that the root CI points to (outgoing)
- With depth > 1, additional columns are added for each level

Each edge carries a label with the relationship type, colour-coded:

| Colour | Relationship type |
|--------|------------------|
| Indigo | HOSTS |
| Orange | DEPENDS_ON |
| Teal | CONNECTED_TO |
| Emerald | PROVIDES_SERVICE |
| Purple | BACKED_UP_BY |

**Canvas controls:**
- **Drag**: pan the graph
- **Mouse wheel**: zoom in/out
- Zoom controls are also available in the bottom right corner

---

### Step 2 — Explore: Table View

Click the **"Table"** button (map header) to switch to the tabular view. It shows all relationships found at the selected depth level:

| Column | Description |
|--------|-------------|
| **Dir.** | `↗ Out.` (outgoing from the root CI) / `↙ In.` (incoming to the root CI) |
| **Source CI** | Name and slug of the source CI |
| **Relationship Type** | Badge with the type, coloured by category |
| **Target CI** | Name and slug of the target CI |
| **Level** | Hop depth (only visible when depth > 1) |

Rows are sorted by level (ascending) and then by relationship type.

#### Export to Excel

In the table view, click **"Export Excel"** to download a `.xlsx` file with all visible relationships. The file is named `dependencias-<ci-slug>.xlsx` and includes the same columns as the table, with automatically adjusted column widths.

---

### Header controls

| Control | Function |
|---------|---------|
| **← Change CI** | Returns to the selection form |
| Levels badge | Shows the active depth |
| **Graph / Table** | Toggles between the two display modes |
| Refresh button | Reloads the relationships without changing the selection |
| **New Relationship** | Opens the modal to create a relationship (ADMIN only) |
| Click on edge (Graph View) | Deletes the selected relationship with confirmation (ADMIN only) |
| 🗑️ icon per row (Table View) | Deletes the relationship in that row with confirmation (ADMIN only) |

### Creating relationships from the map (ADMIN only)

1. With a CI selected, click **"New Relationship"** (top right header)
2. The current CI appears pre-selected as the source
3. Choose the relationship type and the target CI
4. Click **"Create Relationship"** — the graph updates automatically

### Empty state
If the CI has no registered relationships, the map displays a message with a direct button to **"Create first relationship"**.

## 16. Audit Log

> Only available for users with the **ADMIN** role

### Accessing
Click **"🕵️ Audit"** in the sidebar menu.

### What is recorded?
The system automatically records all administrative actions:

| Recorded action | Description |
|-----------------|-------------|
| `CREATE_CI` | Creation of a new CI |
| `CREATE_RELATION` | Creation of a relationship between two CIs |
| `UPDATE_VULN_STATUS` | Change of a vulnerability status |
| `UPDATE_VERIFICATION` | Update of verified EOL/EOS dates |
| `SET_ROLE` | Change of user role |
| `ACTIVATE_USER` | User account activation |
| `DEACTIVATE_USER` | User account deactivation |

### Information recorded per entry
- **Action**: What was done
- **Entity**: On which object (CI, VULNERABILITY, USER…)
- **Entity ID**: Identifier of the affected object
- **User**: Email of the user who performed the action
- **Date and time**: Timestamp with second-level precision

> The Audit Log is **append-only**: records cannot be edited or deleted from the interface, guaranteeing the traceability required by ISO 27001 A.12.4.

## 18. NIS2 / GDPR Resilience Fields

> Available in the **Add CI** and **Edit CI** forms for users with the **ADMIN** role

The platform includes a block of regulatory compliance fields aligned with the **NIS2 Directive** (Network and Information Security), the **ISO 22301** standard (business continuity), and the **GDPR**.

### Available fields

| Field | Type | Description |
|-------|------|-------------|
| **Business Impact (NIS2)** | Enum | Classifies the CI's impact in the event of a failure: `Low`, `Medium`, `High`, `Critical` |
| **Data Classification (GDPR)** | Enum | Sensitivity level of the data: `Public`, `Internal`, `Confidential`, `Restricted` |
| **Recovery Priority** | Number (1–5) | Restoration order in a contingency plan (1 = first to be recovered) |
| **RTO (minutes)** | Number | Recovery Time Objective — maximum tolerable interruption time |
| **RPO (minutes)** | Number | Recovery Point Objective — maximum tolerable data loss in time |
| **Single Point of Failure (SPOF)** | Boolean | Marks the CI as a Single Point of Failure per ISO 22301 |
| **Contains Personal Data (PII)** | Boolean | Indicates whether the CI processes or stores personal data subject to GDPR |

### Visual indicators in the Inventory

CIs with active flags display labels in the name column:

| Label | Colour | Meaning |
|-------|--------|---------|
| `SPOF` | Red | The CI is a single point of failure |
| `PII` | Purple | The CI handles personal data (GDPR) |
| `NIS2 Critical` | Orange | The CI has CRITICAL business impact |

### Visual indicators in the Dependency Map

SPOF nodes appear highlighted with a **red border** and the `SPOF` label in the dependency graph, making it easy to visually identify risks in the topology.

### Use cases by regulation

**NIS2 (Network and Information Security Directive):**
- Classifies CIs by business impact to prioritise the protection of critical assets
- Facilitates mandatory incident notification (NIS2 art. 23) by identifying affected systems

**ISO 22301 (Business Continuity):**
- The RTO/RPO fields feed directly into the Disaster Recovery Plan (DRP)
- The SPOF flag allows identifying bottlenecks in the topology that require redundancy
- The recovery priority defines the restoration order in the BCP

**GDPR (General Data Protection Regulation):**
- Data classification allows inventorying personal data processing activities (GDPR art. 30)
- The PII flag facilitates compliance with the Record of Processing Activities
