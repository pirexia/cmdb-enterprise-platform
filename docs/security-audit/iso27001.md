## Executive Summary

The CMDB Enterprise Platform demonstrates a mature security posture for a web application of its scope, with strong controls in authentication, access management, and audit logging that substantially satisfy the technological controls of ISO/IEC 27001:2022 Annex A. The platform implements multi-factor authentication with mandatory enforcement for admin accounts, a three-tier RBAC model, parameterized SQL throughout, bcrypt password hashing at OWASP-recommended cost factors, immutable audit logs, and TLS-capable deployment behind an nginx gateway. The most critical gap for certification readiness is the absence of a formal Information Security Management System (ISMS) documentation layer — no written information security policy, risk assessment, Statement of Applicability, supplier agreements, or incident response procedure exists within the audited repository. Certification under ISO/IEC 27001:2022 requires both technical controls and organizational management processes; the application-layer controls are at an advanced stage, but the management layer must be established before a certification audit can succeed.

## A.5 — Organizational Controls

### A.5.1 — Policies for Information Security

**Current State:** No formal information security policy document was found in the repository. `CLAUDE.md` and `SECURITY_AUDIT.md` document development practices and security controls, but these are engineering references, not a management-approved information security policy.

**Gap Assessment:** ISO 27001:2022 A.5.1 requires a top-level information security policy approved by management, communicated to all staff, and reviewed at planned intervals. The repository lacks this document entirely.

**Risk Level:** High

**Recommendation:** Draft and obtain management approval for a formal Information Security Policy covering: objectives, scope, principles, roles and responsibilities, and regulatory obligations. Store in a governed document register, publish to all personnel, and schedule annual review.

---

### A.5.2 — Information Security Roles and Responsibilities

**Current State:** Three roles are technically defined in the application: `ADMIN`, `AUDITOR`, `VIEWER` (schema.prisma:10–14, index.ts:279–294). The `requireAdmin` and `requireAudit` middleware enforce these at every endpoint. The sysadmin manual documents operational responsibilities. No formal job descriptions, RACI matrix, or organizational chart exist in the repository.

**Gap Assessment:** Technical RBAC is well-implemented. The gap is at the organizational level: no documented appointment of an Information Security Officer, no written role descriptions, and no accountability matrix for the ISMS itself.

**Risk Level:** Medium

**Recommendation:** Document organizational roles for the ISMS: appoint a named Information Security Officer, define responsibilities for the platform owner, DevOps team, and end users. Maintain these in the governance documentation set.

### A.5.8 — Information Security in Project Management

**Current State:** `CLAUDE.md` defines a "Definition of Done" checklist requiring TypeScript checks, container rebuild, health-check verification, and documentation updates before committing. Security audit history in `SECURITY_AUDIT.md` demonstrates iterative security improvements tied to versioned releases.

**Gap Assessment:** The development workflow embeds security checkpoints, which partially satisfies this control. However, there is no formal security requirements specification for new features, no threat modelling process, and no project-level risk assessment.

**Risk Level:** Medium

**Recommendation:** Formalize a lightweight Secure Development Lifecycle (SDL) policy: require threat modelling for new modules, document security requirements in feature specifications, and include security sign-off in the release gate.

### A.5.12 — Classification of Information

**Current State:** The `DataClassification` enum (`PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED`) is defined in the schema (schema.prisma:83–88) and is an optional field on the `CI` model. The `containsPii` boolean flag also exists on `CI` (schema.prisma:345). Classification fields are available but their use is not enforced by application logic.

**Gap Assessment:** Data classification taxonomy exists at the schema level but there is no enforced policy requiring classification of all records, no handling rules per classification tier, and no technical enforcement preventing unclassified sensitive assets.

**Risk Level:** Medium

**Recommendation:** Define and publish a data classification handling policy. Consider making `dataClassification` mandatory for CIs with `containsPii=true`. Add validation in `CICreateSchema` to require classification when PII flag is set.

### A.5.23 — Information Security for Use of Cloud Services

**Current State:** The platform is deployed on-premise (Docker/RHEL) with optional Microsoft 365 SSO integration via Azure AD (docker-compose.prod.yml:79–84). The Microsoft SSO integration validates `tid`, `aud`, `iss`, `nonce`, and email domain in ID tokens (index.ts:558–559). No cloud storage or external SaaS dependencies beyond Azure AD authentication were identified.

**Gap Assessment:** The SSO integration with Azure AD constitutes a cloud service dependency. No formal cloud service policy, Azure tenant security review, or supplier agreement documentation was found.

**Risk Level:** Low

**Recommendation:** Document the Azure AD dependency as an approved cloud service. Obtain or review Microsoft's compliance certifications (SOC 2, ISO 27001) as part of supplier due diligence. Configure Conditional Access policies in Azure to restrict access to the expected corporate network/device.

## A.7 — Physical and Environmental Security

### A.7.8 — Equipment Siting and Protection

**Current State:** Docker containers run in network-isolated environments. `docker-compose.prod.yml` defines two segregated networks: `cmdb-internal` (PostgreSQL and backend only, `internal: true`, no external routing) and `cmdb-public` (backend and frontend). PostgreSQL port is not exposed to the host (docker-compose.prod.yml:35). The `security_opt: no-new-privileges:true` flag is set on all containers (docker-compose.prod.yml:44–45, 101, 131).

**Gap Assessment:** Network isolation is well-implemented for the containerized deployment. The physical security of the underlying host (RHEL server) depends on the operating environment and is outside the scope of application-layer controls. No documentation of physical data center controls was found in the repository.

**Risk Level:** Low (for application layer)

**Recommendation:** Document the physical location and access controls of the production server in the ISMS. Ensure the data center or server room has appropriate physical access controls (locked cabinets, CCTV, visitor logs).

---

### A.7.9 — Security of Assets Off-Premises

**Current State:** Document storage is configurable via `DOCUMENTS_STORAGE_PATH` and supports NFS mounts (`SYSADMIN_MANUAL.md` lines 230–239). TLS certificates are stored in a named Docker volume (`cmdb-tls-certs`). The `DOCUMENTS_STORAGE_PATH` directory is mounted into the backend container with read/write access.

**Gap Assessment:** When document storage uses NFS, data travels over the network to an external mount. The sysadmin manual does not require NFS encryption (e.g., NFS over TLS or Kerberos). TLS private keys (`server.key`) are stored in a Docker volume with permissions set to `chmod 600` per the sysadmin manual, but no formal key custody procedure exists.

**Risk Level:** Medium

**Recommendation:** Require NFS-over-TLS or equivalent encryption when using network-attached document storage. Document a key management procedure for TLS private keys: who holds the passphrase, how keys are rotated (current cert validity is 365 days), and how to handle key compromise.

## A.8 — Technological Controls

### A.8.2 — Privileged Access Rights

**Current State:** Privileged (write) access is restricted to the `ADMIN` role via `requireAdmin` middleware (index.ts:279–284). All `POST`, `PATCH`, `DELETE` operations on CIs, contracts, documents, licenses, users, and master data require `ADMIN` role. The `AUDITOR` role has read access and exclusive access to audit logs. User accounts run as non-root `node` user inside Docker containers (`docker-compose.prod.yml` comment at line 9: "Non-root node user in all application containers"). The `no-new-privileges:true` container security option prevents privilege escalation.

**Gap Assessment:** Privileged access is strongly controlled at the application layer. The gap is the absence of a formal privileged access management (PAM) review schedule — no periodic re-certification of ADMIN accounts, and no documented break-glass procedure for emergency access.

**Risk Level:** Low

**Recommendation:** Implement a quarterly review of ADMIN role assignments using the audit log (`GET /api/audit-logs`). Document a break-glass procedure for emergency access when the only admin account is unavailable.

---

### A.8.3 — Information Access Restriction

**Current State:** All protected API endpoints require JWT authentication via `authenticateToken` middleware (index.ts:236–277). The middleware verifies the JWT signature with algorithm pinning (`algorithms: ['HS256']`, index.ts:247), checks the `mfaSetupRequired` flag to restrict limited tokens to MFA setup endpoints only (index.ts:253–260), and performs a live database check to reject tokens for deactivated users (index.ts:264–276). Role-based restrictions (`requireAdmin`, `requireAudit`) are applied at the endpoint level. `GET /api/users` is accessible to all authenticated roles (any authenticated user can list users — index.ts:880–894).

**Gap Assessment:** The `GET /api/users` endpoint returns user details including `mfa_enabled` status and `sso_external_id` to any authenticated user including `VIEWER`. While passwords are excluded, this may expose more user metadata than necessary for the viewer role under a least-privilege principle.

**Risk Level:** Low

**Recommendation:** Review whether `VIEWER` role needs to access the full user list. Consider restricting `GET /api/users` to `ADMIN` or `AUDITOR` roles, or filtering the response to exclude sensitive fields (`mfa_enabled`, `sso_external_id`) for `VIEWER` role callers.

### A.8.4 — Access to Source Code

**Current State:** `.gitignore` excludes `.env` files and credential files from the repository. The `CLAUDE.md` notes that `.env.example` contains only placeholder values. No hardcoded secrets were found in the reviewed source code. `JWT_SECRET` is read from environment variables and the server refuses to start in production if it is absent (index.ts:47–54).

**Gap Assessment:** Source code access controls depend on the git repository hosting (GitHub, per sysadmin manual). No repository access control policy, branch protection rules, or developer onboarding security requirements were documented. The single-file backend architecture (~4,100 lines in `index.ts`) creates a large attack surface for any developer with write access.

**Risk Level:** Medium

**Recommendation:** Document repository access control policy: require branch protection on `main` and `develop`, require PR reviews before merge, restrict force-push access. Consider splitting the monolithic `index.ts` into domain-separated route modules to reduce the blast radius of a compromised developer account.

### A.8.5 — Secure Authentication

**Current State:** The platform implements a multi-layered authentication strategy:
- **Local auth:** bcrypt comparison with cost factor 12 (index.ts:65, `BCRYPT_ROUNDS=12`), role-aware password policy (16 chars for ADMIN, 12 for others), complexity rules, common-password blocklist (~150 entries), password history (last 20, configurable) (index.ts:357–411).
- **MFA (TOTP):** Mandatory for ADMIN (short-lived 15-min limited JWT if not configured, index.ts:852–857), suggested for others. TOTP validated via `speakeasy` RFC 6238 with `window: 1` (index.ts:838). Server-side pending secret prevents client-controlled seed injection (index.ts:43 in SECURITY_AUDIT.md).
- **Trusted devices:** 32-byte cryptographically random token bound to IP and User-Agent at creation (index.ts:797–807, 816–828), stored in `trusted_devices` table, TTL configurable (default 30 days), cleaned up by daily cron (index.ts:3565–3572).
- **SSO (Microsoft 365):** PKCE flow with state/nonce validation, JWKS signature verification, `tid`/`aud`/`iss`/`nonce`/domain validation (index.ts:543–560), one-time exchange code avoids JWT in redirect URL (index.ts:655–664).
- **LDAP:** RFC 4514/4515 escaping via `escapeLdap()`, 5-second timeout, fallback to local on failure (SYSADMIN_MANUAL.md:337–340).
- **Rate limiting:** 10 failed attempts / 15 min on `POST /api/auth/login` (`skipSuccessfulRequests: true`, index.ts:129–136), 20 req/15 min on SSO callbacks (index.ts:139–145), 300 req/min general API limiter (index.ts:182–190).
- **JWT:** HS256 algorithm pinned at sign and verify, 8h expiry, client-side expiry checks in `AuthContext.tsx` with 60s periodic check.

**Gap Assessment:** Authentication controls are comprehensive and meet or exceed NIST SP 800-63B Level 2 requirements. A minor gap exists: the TOTP `window: 1` allows codes from 30 seconds before/after the current window, which is standard but worth documenting. No account lockout is implemented beyond rate limiting per IP — a distributed attack from multiple IPs could bypass the per-IP rate limit.

**Risk Level:** Low

**Recommendation:** Consider adding an account-level lockout mechanism (e.g., track failed attempts per user in the database) as a defense-in-depth measure against distributed credential-stuffing attacks. Document the TOTP window tolerance in the security policy.

### A.8.7 — Protection Against Malware

**Current State:** `npm audit` results show 0 vulnerabilities in both frontend and backend as of 2026-03-15 (SECURITY_AUDIT.md). File upload validation implements both extension allowlist and magic byte verification (index.ts:2771–2802). SVG files are excluded from the allowed extension set (index.ts:2772–2773), preventing stored XSS via inline SVG rendering. Downloaded files that are not in the safe MIME type allowlist are forced to `Content-Disposition: attachment` (index.ts:3083–3091). No runtime container antivirus scanning was found.

**Gap Assessment:** Dependency vulnerability management and file upload security are strong. The container runtime has no malware scanning layer, and there is no documented process for scheduled dependency audits or CVE monitoring for `node`, `postgresql`, and `nginx` base images.

**Risk Level:** Medium

**Recommendation:** Establish a scheduled dependency audit cadence (monthly `npm audit` minimum). Implement image scanning in the CI/CD pipeline (e.g., Trivy or Docker Scout) to detect vulnerabilities in base images (`node:alpine`, `postgres:16-alpine`, `nginx:1.30`). Document the patch management timeline for critical CVEs (e.g., remediate within 72 hours for CVSS ≥ 9.0).

### A.8.11 — Data Masking

**Current State:** Passwords are never returned in API responses — the `users` query in `GET /api/users` explicitly excludes the `password` field (index.ts:882–884). MFA secrets (`mfa_secret`, `mfa_pending_secret`) are stored in the database but not returned in API responses. The `CI_INCLUDE` object for `businessOwner` and `technicalLead` relations uses `select` to return only `id`, `username`, `email` — not password fields (index.ts:421–422).

**Gap Assessment:** Sensitive authentication data is masked from API responses. However, the `containsPii` and `dataClassification` fields on CIs are informational flags — there is no technical enforcement masking PII fields in CI data based on the classification level. The `assignedUser` and `userDni` fields on `CI` (schema.prisma:300–302) store personal identifiers without any access-level-based masking.

**Risk Level:** Medium

**Recommendation:** Consider implementing field-level masking for `userDni` and `assignedUser` fields in CI API responses when the requesting user has `VIEWER` role. For `CONFIDENTIAL` or `RESTRICTED` classified CIs, consider restricting full-detail access to `ADMIN` and `AUDITOR` roles.

### A.8.12 — Data Leakage Prevention

**Current State:** CORS is configured with a strict allowlist from `CORS_ORIGINS` environment variable; unlisted origins are blocked and logged (index.ts:104–122). Request body size is limited to 2MB (index.ts:124). JWT tokens are not passed in URL parameters for downloads (fixed in v1.1.0, SECURITY_AUDIT.md). Stack traces and raw Prisma errors are not returned to clients — all 500 responses use `{ error: 'Internal server error' }` (fixed in v1.6.4). The `Referrer-Policy: strict-origin-when-cross-origin` header limits information leakage via HTTP Referer. No DLP tooling or egress filtering at the network layer was documented.

**Gap Assessment:** Application-layer data leakage prevention is strong. The gap is at the network and operational layers: no egress filtering for outbound connections from containers (the backend calls `endoflife.date` API), no DLP scanning on document uploads, and no monitoring for unusual bulk data exports.

**Risk Level:** Medium

**Recommendation:** Implement egress allowlisting for outbound container network connections. Audit the `eolService.ts` external API call to ensure no SSRF vectors exist. Consider adding a maximum-records guard on bulk export endpoints and logging unusually large data retrievals.

### A.8.15 — Logging

**Current State:** The `audit_logs` table (schema.prisma:416–428) records `action`, `entity`, `entity_id`, `user_email`, and `created_at` for all write operations. Logged events include: `LOGIN`, `LOGIN_SSO`, `CREATE_CI`, `UPDATE_CI`, `DELETE_CI`, `SET_ROLE`, `ACTIVATE_USER`, `DEACTIVATE_USER`, `CHANGE_PASSWORD`, `RESET_PASSWORD`, `CREATE`/`UPDATE`/`DELETE` for documents, licenses, and master data. All timestamps use PostgreSQL `now()` for consistent clock source. The `AUDITOR` role has exclusive read access to audit logs via `GET /api/audit-logs` (protected by `requireAudit`).

**Gap Assessment:** Application-level audit logging is comprehensive and covers all required CRUD operations on sensitive entities. The following gaps exist:
1. **Missing fields:** The `AuditLog` model does not store the changed values (`before`/`after` snapshots), making it impossible to reconstruct what was changed, only that a change occurred.
2. **Login failures are not logged:** Failed authentication attempts are not recorded in `audit_logs`, which hinders incident investigation and brute-force detection.
3. **Read access is not logged:** `GET` operations on sensitive data (CI details, user lists, documents) are not audited.
4. **Retention:** The default `AUDIT_RETENTION_DAYS=365` purges audit logs after one year. Some compliance frameworks require longer retention.

**Risk Level:** Medium

**Recommendation:** (1) Add `before`/`after` JSON columns to `audit_logs` for write operations to enable full change reconstruction. (2) Log failed login attempts with a `LOGIN_FAILED` action. (3) Consider logging reads of sensitive or RESTRICTED-classified CIs. (4) Review audit log retention policy against applicable regulatory requirements (NIS2, GDPR); consider archiving to immutable storage rather than deleting.

### A.8.16 — Monitoring Activities

**Current State:** Application-level events are logged as described in A.8.15. The alert engine sends daily email reports for EOL/EOS alerts and contract expirations. Rate limiting logs blocked requests to `console.warn`. Docker container health checks are configured for PostgreSQL (docker-compose.prod.yml:38–43).

**Gap Assessment:** No centralized SIEM integration was found. Container stdout/stderr logs are available via `docker logs` but no log aggregation, correlation, or alerting infrastructure (e.g., ELK, Splunk, Grafana Loki) was documented. **Risk Level:** Medium

**Recommendation:** Integrate container logs with a centralized log management solution. Define and implement alert rules for: repeated login failures across users, ADMIN account creation, bulk data access, and unexpected after-hours access. Consider exporting `audit_logs` to a SIEM for correlation.

### A.8.20 — Network Security

**Current State:** Production compose defines two segregated Docker networks: `cmdb-internal` (PostgreSQL ↔ backend, `internal: true`) and `cmdb-public` (backend ↔ frontend ↔ host). PostgreSQL is not exposed on any host port in production (docker-compose.prod.yml:34–36). The `no-new-privileges:true` security option is set on all containers. CORS restricts cross-origin access. The nginx configuration was not found at the expected path but is referenced in `CLAUDE.md` as the TLS gateway.

**Gap Assessment:** Network segmentation is well-implemented using Docker networking. The gap is the missing nginx configuration file (`nginx/conf.d/frontend.conf` returned a file-not-found error), making it impossible to verify nginx-level security controls (TLS version, cipher suites, HTTP headers). The backend is also exposed on `BACKEND_PORT` directly to the host in the prod compose file (docker-compose.prod.yml:89), bypassing the nginx gateway.

**Risk Level:** High

**Recommendation:** The backend should not be directly exposed on the host port in production; remove or remove the `ports` directive from the backend service in `docker-compose.prod.yml` and route all traffic through nginx. Restore the nginx configuration file. Configure nginx to: allow only TLS 1.2+, use strong cipher suites, enforce HSTS, and disable server version disclosure.

### A.8.21 — Security of Network Services

**Current State:** The nginx gateway provides TLS termination (HSTS header configured with `max-age=31536000; includeSubDomains`, SECURITY_AUDIT.md). The backend uses Helmet for security headers including `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, and `Referrer-Policy: strict-origin-when-cross-origin` (index.ts:90–102). SMTP is configured for EOL alerts with optional TLS via `SMTP_SECURE` env var.

**Gap Assessment:** The nginx configuration file is missing, preventing verification of TLS cipher suite configuration. The SMTP configuration defaults to `SMTP_SECURE=false` (docker-compose.prod.yml:65), meaning email alert traffic may be sent in cleartext. The `LDAP_TLS_REJECT_UNAUTHORIZED` variable defaults to `1` (verify certs) but the sysadmin manual advises setting it to `0` for internal CAs (SYSADMIN_MANUAL.md:335), which disables certificate chain validation.

**Risk Level:** Medium

**Recommendation:** Enable SMTP TLS in production (`SMTP_SECURE=true` with port 465, or STARTTLS on port 587). Document that `LDAP_TLS_REJECT_UNAUTHORIZED=0` must only be used with a properly trusted internal CA, never in internet-facing deployments. Restore and harden the nginx configuration.

### A.8.24 — Use of Cryptography

**Current State:**
- **JWT:** HS256 algorithm pinned at both `jwt.sign()` and `jwt.verify()` with `algorithms: ['HS256']` allowlist, preventing algorithm-confusion attacks including `alg: none` (index.ts:247, 639, 791, 855).
- **Password hashing:** bcrypt with cost factor 12 (OWASP recommended, index.ts:65). Plaintext passwords are never stored or returned.
- **MFA secrets:** TOTP secrets stored in database (`mfa_secret` column, schema.prisma:104). Secrets are not encrypted at rest at the application layer; they rely on database-level access controls.
- **Trusted device tokens:** 32 bytes from `crypto.randomBytes` (cryptographically secure, index.ts:624, 796).
- **TLS:** RSA 2048-bit certificates, SHA-256 (SECURITY_AUDIT.md). HSTS with preload is configured when HTTPS is enabled.
- **Key management:** `JWT_SECRET` must be set via environment variable; server exits in production if absent (index.ts:47–54). No automated key rotation mechanism exists.

**Gap Assessment:** Cryptographic controls are generally strong. The main gap is the lack of TOTP secrets encryption at rest — `mfa_secret` and `mfa_pending_secret` are stored as plaintext Base32 strings in the database. If the database is compromised, all MFA seeds are exposed. Additionally, there is no JWT secret rotation procedure and no documented cryptographic key management policy.

**Risk Level:** Medium

**Recommendation:** Encrypt TOTP secrets at rest using AES-256-GCM with a key derived from a KMS or environment-level secret. Document a JWT secret rotation procedure (rotation requires coordinated re-login of all active sessions). Formalize a cryptographic policy defining approved algorithms, key lengths, and rotation schedules.

### A.8.27 — Secure System Architecture and Engineering Principles

**Current State:** The architecture is documented in `docs/ARCHITECTURE.md`. Key security principles implemented: network segmentation (Docker networks), defense in depth (nginx gateway + application-layer auth), least privilege (RBAC, non-root containers), fail-secure (JWT_SECRET required in production, `active` check on every request), input validation at API boundaries (Zod), and output encoding (no raw SQL string concatenation).

**Gap Assessment:** The architecture is sound for its scale. The monolithic single-file backend (`index.ts` ~4,100 lines) creates a maintainability risk and makes security review harder. There is no documented threat model and no formal security architecture review process.

**Risk Level:** Low

### A.8.28 — Secure Coding

**Current State:** Evidence of secure coding practices:
- All `$queryRaw`/`$executeRaw` use parameterized tagged template literals (no string concatenation).
- LIKE wildcards escaped before interpolation (`%`, `_`, `\`) with `ESCAPE '\\'` clause (index.ts:2717–2721).
- LDAP injection prevented via `escapeLdap()` RFC 4514/4515 (SECURITY_AUDIT.md HIGH fixes).
- File uploads validated by extension allowlist + magic byte verification (index.ts:2795–2802).
- UUID filenames for stored documents prevent path traversal (index.ts:3000).
- SVG and other active content types blocked from inline serving (index.ts:3085–3091).
- Error messages do not expose internal details (50+ catch blocks standardized in v1.6.4).
- `npm audit` shows 0 vulnerabilities (as of 2026-03-15).

**Gap Assessment:** Secure coding practices are strong and well-documented. The gap is the absence of peer review requirements for security-sensitive code, no code signing, and no documented procedure for handling third-party library vulnerabilities discovered post-release.

**Risk Level:** Low

**Recommendation:** Require code review by a security-aware team member for changes to authentication, authorization, and data persistence code. Document a vulnerability disclosure and patch management procedure.

### A.8.33 — Test Information

**Current State:** The `docs/mocks/` directory exists, suggesting mock data is available for testing. The sysadmin manual describes seed data for initial deployment (admin and auditor accounts with default credentials). The development Docker Compose includes Adminer for database access.

**Gap Assessment:** No formal test data management policy was found. The seed data uses predictable default credentials (`Admin1234!`, `Audit1234!`) which are documented in the sysadmin manual (SYSADMIN_MANUAL.md lines 143–147). While the manual warns to change these immediately, there is no technical enforcement preventing their use in production.

**Risk Level:** Low

**Recommendation:** Implement a first-login forced password change for seeded accounts. Consider generating random seed passwords printed to the installation log rather than using fixed defaults. Document a test data management policy prohibiting use of real production data in development/staging environments.

### A.8.34 — Protection of Information Systems During Audit Testing

**Current State:** The audit log table is insert-only via raw SQL in application code. There is no `UPDATE` or `DELETE` path for audit records in the API. The `AUDITOR` role can only read audit logs (`requireAudit` middleware), not modify them. The audit log purge is a server-side scheduled cron job controlled by the `AUDIT_RETENTION_DAYS` environment variable, not accessible via the API.

**Gap Assessment:** Audit log integrity is well-protected at the application layer. However, any user with database credentials (e.g., via the `DATABASE_URL` connection string) can directly delete or modify audit records in PostgreSQL. No database-level row-level security (RLS) or trigger-based immutability enforcement exists in the Prisma schema.

**Risk Level:** Medium

**Recommendation:** Implement PostgreSQL Row-Level Security on `audit_logs` to permit INSERT but block UPDATE and DELETE for the application database user. Consider streaming audit logs to an external append-only log store (e.g., syslog, S3 with object lock) as a secondary tamper-evident record. This would address the ISO 27001 requirement that audit information be protected from alteration.

## Certification Readiness Assessment

The CMDB Enterprise Platform v2.0.1 has a technically strong security posture that satisfies the majority of ISO/IEC 27001:2022 Annex A **technological controls** (A.8). The application implements parameterized SQL throughout, a robust multi-factor authentication system, comprehensive audit logging, meaningful network segmentation via Docker, strong cryptographic controls, and active dependency vulnerability management. These controls collectively represent a mature and defensible implementation.

However, the platform is **not currently ready for ISO/IEC 27001:2022 certification** due to critical gaps in the **organizational and people controls** (A.5 and A.6). Certification requires an operational ISMS that includes:

1. A management-approved Information Security Policy (A.5.1) — **not present**
2. A formal risk assessment and risk treatment plan — **not present**
3. A Statement of Applicability (SoA) documenting which Annex A controls apply and how — **not present**
4. Evidence of security awareness training for all users (A.6.3) — **not present**
5. Incident response procedures (A.6.8) — **not present**
6. Supplier/third-party security agreements (A.5.23 for Azure AD dependency) — **not present**
7. Independent security review evidence (A.5.35) — **not present**

Additionally, two technical findings require remediation before a certification audit:

- The backend service is directly port-exposed in `docker-compose.prod.yml`, partially bypassing the nginx gateway.
- Audit log immutability relies only on application-layer controls; database-level protections should be added.

**Estimated timeline to certification readiness:** 3–6 months, with the primary effort being ISMS documentation and organizational process establishment rather than additional technical development.
