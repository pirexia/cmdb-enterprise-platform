# n8n Provisioning Resilience (#178 · #179) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make backend n8n auto-provisioning distinguish an invalid API key (fail fast, actionable log) from "n8n not ready yet" (keep retrying), widen the cold-start retry window, add an n8n readiness healthcheck for observability, and give operators a self-healing path for a stale `N8N_API_KEY`.

**Architecture:** Two GitHub issues, one subsystem (`backend/src/modules/n8n-provisioning/`). The code fix introduces a status-bearing error type (`N8nApiError`) thrown by the thin HTTP client, so both the boot-time provisioner (`onBoot.ts`) and the on-demand resync route (`router.ts`) can branch on `401/403` (credential invalid — #178) vs. connectivity errors (n8n starting — #179). The retry window widens from 60s → 120s to cover a full cold-stack start (#179). A pure-observability healthcheck is added to `n8n-main` in both compose files — deliberately **without** wiring it as a hard `depends_on` of the backend (rationale in Task 4). Operational steps to realign the live key are a runbook, not code.

**Tech Stack:** TypeScript (Express 5, Node 22), Jest, Prisma 6, Podman Compose, n8n public REST API (`/api/v1`), bash deploy scripts.

## Global Constraints

- **Verbatim from CLAUDE.md — A09 (Logging):** never dump full HTTP response bodies or credential values in logs; log status codes and generic actionable text only.
- **A02 / A.8.12:** `N8N_API_KEY` comes from env (`.env`) only — never hardcoded, never printed in full.
- **ISO 22301 / NIS2 — no new SPOF:** the core backend API must start even when the optional n8n integration is down. Do **not** make the backend block on n8n health.
- **A.8.15:** the resync route already writes an `AuditLog`; keep that intact.
- **DoD (CLAUDE.md):** `cd backend && npx tsc --noEmit` passes with 0 new errors (the two known `license`/`licenseUser` Prisma errors are pre-existing — ignore). Compose changes must be tested in the **dev** compose before prod.
- **TDD:** every code change starts with a failing test.
- **Known deploy caveat (memory `ops_podman_compose_build_cache_bug`):** selective `up -d <svc>` can deadlock on pod deps; use a full `down`/`up` when it does — and only with the user's OK (service interruption).

// backend/src/modules/n8n-provisioning/errors.ts
/**
 * n8n-provisioning · error tipado del cliente HTTP de la API de n8n.
 *
 * Lleva el `status` HTTP para que las capas superiores (onBoot, router) puedan
 * distinguir una credencial inválida (401/403 — no reintentable) de un fallo de
 * conectividad (n8n aún no listo — reintentable). Vive en su propio módulo para
 * que `instanceof` funcione en tests donde `apiClient.js` está mockeado.
 */
export class N8nApiError extends Error {
  constructor(
    public readonly status: number,
    public readonly method: string,
    public readonly path: string,
  ) {
    super(`n8n API ${method} ${path} -> ${status}`);
    this.name = 'N8nApiError';
  }

  /** true si el fallo es de autenticación/autorización (credencial inválida). */
  get isAuthError(): boolean {
    return this.status === 401 || this.status === 403;
  }
}
```

      let attempt = 0;
      while (attempt < maxRetries) {
        try {
          await client.listWorkflows();
          break; // n8n listo
        } catch (err) {

            return;

          if (attempt >= maxRetries) {
            const windowSecs = Math.round((maxRetries * retryDelayMs) / 1000);
            console.error(
              `${LOG_PREFIX} n8n no disponible tras ${maxRetries} intentos (~${windowSecs}s); aprovisionamiento cancelado.`
            );
            return;
          }
          console.log(`${LOG_PREFIX} n8n no responde (intento ${attempt}/${maxRetries}); reintentando en ${retryDelayMs}ms...`);
          await sleep(retryDelayMs);
        }
      }
```

**Design note (why no `depends_on` on the backend):** Issue #179 lists "add `depends_on: n8n-main: service_healthy` to backend" as an option. We deliberately **reject** it: it would make the optional n8n integration a hard startup dependency of the core CMDB API — if n8n never becomes healthy, the whole platform would fail to start. That violates NIS2 (no new single point of failure), ISO 22301 (RTO < 15 min from clean pull), and connector decision D1 (n8n is optional). Instead we add the healthcheck to `n8n-main` for **observability only** (operators and the `install.sh`/`update.sh` scripts already poll `/healthz`), and rely on the backend's own widened 120s backoff (Task 3) for cold-start timing. The backend's `depends_on` block stays `postgres` + `ollama` only.
